# Узел-хранитель Backpeer в Docker

Узел-хранитель (`node`) отдаёт чужому бэкапу место на диске. Клиент шифрует
данные у себя и режет их на фрагменты, поэтому узел не видит ни содержимого,
ни имён файлов и не хранит ключей учётной записи. В контейнере работает
только эта роль: приложение, бэкап по расписанию и вход в учётную запись
остаются на устройстве владельца.

Инструкция — для любой машины с Docker: сервера, домашнего компьютера, NAS
или Raspberry Pi. Она покрывает установку, привязку узла к учётной записи и
повседневное управление: проверку, паузу, пределы скорости, обновление,
резервную копию и выход из сети.

## Что понадобится

- Docker Engine 24 или новее и Compose v2 (`docker compose`), 64-битная
  Linux-система. Подойдёт и Docker Desktop, но постоянный узел лучше держать
  на машине, которая работает круглосуточно.
- Не меньше 100 ГБ под фрагменты: координатор по умолчанию не принимает
  узлы с меньшей ёмкостью. Занятое место растёт постепенно, сразу весь диск
  не нужен.
- Исходящий доступ по HTTPS к координатору. Для прямых соединений с
  клиентами желателен открытый порт 7340 TCP и UDP; если открыть его нельзя,
  узел работает через relay.
- Синхронизация часов (NTP): талоны координатора действуют с допуском
  пять минут.
- Права root на хосте нужны только для установки Docker, проброса порта и
  подготовки каталога фрагментов. Сам узел работает в контейнере от
  непривилегированного пользователя `fs-node` (uid и gid 10003).

## Быстрый старт

Создайте каталог и два файла рядом с ним:

```sh
mkdir -p backpeer-node
cd backpeer-node
```

`.env` — версия образа и адрес координатора (его выдают при приглашении в
бету):

```text
BACKPEER_VERSION=latest
BACKPEER_COORDINATOR_URL=https://coordinator.example
```

`compose.yaml`:

```yaml
services:
  node:
    image: ghcr.io/3davinci/backpeer/node:${BACKPEER_VERSION:-latest}
    restart: unless-stopped
    # Демон завершает начатые передачи до 30 секунд; Docker по умолчанию
    # убивает контейнер через 10 — даём ему время.
    stop_grace_period: 40s
    environment:
      FS_NODE_COORDINATOR_URL: ${BACKPEER_COORDINATOR_URL:?Укажите адрес координатора в .env}
      # Сколько места отдать под фрагменты. 1 ТБ; не меньше 100 ГБ.
      FS_NODE_STORAGE_QUOTA_BYTES: "1000000000000"
    volumes:
      - node-data:/var/lib/fs-node
    ports:
      - "7340:7340/tcp"
      - "7340:7340/udp"

  # Только для управления: в образе узла нет `cli`. Запускается по
  # требованию (`--profile tools`), в обычном `up` не участвует.
  cli:
    image: ghcr.io/3davinci/backpeer/cli:${BACKPEER_VERSION:-latest}
    profiles: ["tools"]
    # Тот же пользователь, что у узла: иначе локальный API узла не пустит.
    user: "10003:10003"
    environment:
      FS_HOME: /tmp/backpeer-cli
    volumes:
      - node-data:/var/lib/fs-node
    entrypoint: ["cli"]

volumes:
  node-data:
    name: backpeer-node-data
```

Привяжите узел к учётной записи. Контейнер создаст ключи, напечатает код и
QR-код и будет ждать подтверждения:

```sh
docker compose run --rm node pair
```

На устройстве, где вы уже вошли в учётную запись, выполните
`cli node pair <код>` (или откройте раздел «Хранитель» в приложении) и
сверьте отпечаток узла с показанным в контейнере. Код действует 10 минут;
просроченный — начните привязку заново. После строки «Узел привязан» запустите
службу:

```sh
docker compose up -d
docker compose ps
```

Столбец `STATUS` через полминуты покажет `healthy`: демон отвечает по
локальному API. Если в `ps` видно `unhealthy` или контейнер перезапускается,
смотрите журнал:

```sh
docker compose logs -f --tail=100 node
```

## Настройки

Настройки задаются переменными `FS_NODE_*`: имя — путь ключа из `node.yaml`
заглавными буквами через `_` (`storage.quota_bytes` →
`FS_NODE_STORAGE_QUOTA_BYTES`). Переменные важнее файла. Неизвестный ключ —
ошибка при запуске, поэтому опечатку видно сразу.

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `FS_NODE_COORDINATOR_URL` | — | Адрес координатора (`https://…`). Без него узел не регистрируется и не принимает фрагменты |
| `FS_NODE_STORAGE_QUOTA_BYTES` | `100000000000` | Сколько места отдать под фрагменты (100 ГБ — минимум координатора) |
| `FS_NODE_STORAGE_FREE_RESERVE_BYTES` | `2000000000` | Сколько места оставлять свободным на диске: фрагмент, после которого останется меньше, не принимается |
| `FS_NODE_STORAGE_DIR` | папка данных | Куда класть фрагменты и индекс — например, на другой диск (раздел «Диск и данные») |
| `FS_NODE_LISTEN_PORT` | `7340` | Порт приёма TCP и UDP; внутри контейнера менять смысла нет |
| `FS_NODE_LISTEN_ENDPOINTS` | — | Адреса `хост:порт`, которые узел сообщает координатору всегда; нужны, если внешний порт не 7340 (раздел «Порты, NAT и relay») |
| `FS_NODE_LISTEN_PORT_MAPPING` | `off` в образе | Проброс порта на роутере по UPnP, PCP или NAT-PMP. В контейнере выключен: из сети Docker узел роутера не видит |
| `FS_NODE_LISTEN_RELAY` | `auto` | Приём через relay: `auto` — когда своих адресов нет, `on` — всегда, `off` — никогда |
| `FS_NODE_LIMITS_UPLOAD_BYTES_PER_SECOND` | `0` | Предел отдачи, байт в секунду; `0` — без предела |
| `FS_NODE_LIMITS_DOWNLOAD_BYTES_PER_SECOND` | `0` | Предел приёма, байт в секунду; `0` — без предела |
| `FS_NODE_LOG_LEVEL` | `info` | `fine`, `info`, `warning`, `severe` |
| `FS_NODE_COORDINATOR_CHANNEL` | `true` | Держать канал команд координатора; `false` — команды (ремонт, аудит, сведение) до узла не доходят |
| `FS_NODE_SHUTDOWN_GRACE_SECONDS` | `30` | Сколько ждать завершения начатых передач при остановке |
| `FS_NODE_CERT_FILE` | — | Только для точки входа образа: сертификат узла, смонтированный в контейнер (раздел «Привязка») |
| `FS_NODE_CONFIG` | `<данные>/node.yaml` | Файл настроек YAML вместо переменных; смонтируйте его в контейнер и задайте путь |

Остальные ключи — расписание пределов, проверка целостности, число
соединений — перечислены в документации проекта; в Docker почти всегда
достаточно переменных выше.

**Постоянные и временные пределы.** Значения из переменных действуют после
перезапуска контейнера. Команда `cli node limits` меняет пределы до
перезапуска — удобно, чтобы быстро притормозить узел. Расписание «днём
медленнее» задаётся в `node.yaml` ключом `limits.schedule` и переживает
перезапуск; расписание действует поверх основных пределов.

## Порты, NAT и relay

Узлу нужно принимать входящие соединения — по TCP, а после сведения через
координатор ещё и по UDP. В примере оба порта опубликованы на тот же номер
7340.

- **Порт на роутере.** Проброс порта в образе выключен: из сети Docker узел
  не видит UPnP-роутер. Пробросьте 7340 TCP и UDP на хост с контейнером
  вручную. Docker опубликует их в контейнер.
- **Внешний порт не 7340.** Если на роутере внешний порт отличается,
  координатор проверяет не тот порт, который слышит узел, и узел останется
  «недоступен извне». Укажите адрес явно, например
  `FS_NODE_LISTEN_ENDPOINTS=home.example.org:8340` (можно несколько через
  запятую). Координатор такие адреса не проверяет, но сообщает клиентам.
- **Проверка достижимости.** Если внешний порт совпадает с 7340, узел сам
  просит координатора проверить адрес, с которого пришёл запрос. Итог виден
  в `cli node status`: «доступен извне (адрес)» или «извне недоступен».
- **Без внешнего адреса.** Узел за симметричным NAT, двойным NAT или без
  проброса работает через relay: соединения идут через публичный сервер,
  relay видит только шифротекст. `FS_NODE_LISTEN_RELAY=auto` включает это
  автоматически, когда у узла нет адресов.
- **Файрвол.** Разрешите входящие 7340 TCP и UDP и исходящие HTTPS к
  координатору. UDP нужен для сведения с узлами за NAT; без него останутся
  TCP и relay.

Проверить, как узел видит сеть:

```sh
docker compose --profile tools run --rm cli \
  node status --node-data /var/lib/fs-node
```

В строке «Приём соединений» будет порт, проброс и итог проверки достижимости;
в строке про координатора — открыт ли канал команд. Если узел отмечен
`needs_relay`, соединения пойдут через relay — это нормально, но медленнее
прямых.

## Привязка к учётной записи

Узел не может принимать фрагменты без сертификата, подписанного устройством
владельца. Два способа:

**По одноразовому коду (обычный).** Остановите узел, если он запущен, и
выполните `docker compose run --rm node pair`. Контейнер напечатает код,
срок действия, отпечаток и QR. На устройстве с учётной записью выполните
`cli node pair <код>` или откройте «Хранитель» в приложении, сверьте
отпечаток и подтвердите. После успешной привязки запустите службу:
`docker compose up -d`.

**Сертификатом (если код недоступен).** На устройстве владельца выпустите
сертификат для ключей узла:

```sh
docker compose run --rm node init --json   # напечатает node_id и node_dh
cli node-cert --node-id … --node-dh … --out node.cert
```

Положите `node.cert` рядом с `compose.yaml` и добавьте в службу `node`:

```yaml
    environment:
      FS_NODE_CERT_FILE: /run/secrets/node.cert
    volumes:
      - node-data:/var/lib/fs-node
      - ./node.cert:/run/secrets/node.cert:ro
```

При каждом запуске точка входа импортирует сертификат. Сертификат
принимается только на ключи этого узла: чужой или с неверной подписью
контейнер отвергнет и завершится с ошибкой.

После привязки перезапустите узел, если он работал без сертификата:
`docker compose up -d --force-recreate node`. Отозванное устройство
перестаёт проходить рукопожатие с узлами, поэтому отзыв в приложении
действует и здесь.

## Проверка

```sh
docker compose ps                                  # healthy — демон отвечает
docker compose exec node node health               # код 0 — локальный API жив
docker compose logs -f --tail=100 node             # журнал JSON Lines
docker compose --profile tools run --rm cli \
  node status --node-data /var/lib/fs-node          # состояние узла
```

В журнале при нормальном запуске есть события `started`, `listening`,
`registered`, `channel_opened`. Дальше раз в несколько минут идут heartbeat
(по каналу или HTTP); ошибки связи узел не роняет, а повторяет с паузой.

Что смотреть в `cli node status`:

- «Место» — занято и сколько ещё узел примет;
- «Фрагментов» — сколько хранится и сколько повреждено (повреждённые узел
  не выдаёт и сообщает о них координатору);
- «Приём соединений» — порт, проброс и доступность извне;
- «Координатор» — регистрация, время последней связи, канал команд.

Счётчики фоновой проверки целостности — в `cli node stats`.

## Управление

В таблице длинная часть `docker compose --profile tools run --rm cli`
сокращена до `…`.

| Задача | Команда |
|---|---|
| Состояние | `docker compose --profile tools run --rm cli node status --node-data /var/lib/fs-node` |
| Статистика с запуска | `docker compose --profile tools run --rm cli node stats --node-data /var/lib/fs-node` |
| Пауза (новые передачи не начинаются, heartbeat идёт) | `… node pause --node-data /var/lib/fs-node` |
| Снять паузу | `… node resume --node-data /var/lib/fs-node` |
| Пределы до перезапуска | `… node limits --upload 2000000 --download 4000000 --node-data /var/lib/fs-node` |
| Перезапуск | `docker compose restart node` |
| Остановка | `docker compose stop node` |
| Запуск | `docker compose up -d node` |
| Журнал | `docker compose logs -f --tail=100 node` |
| Обновление образа | `docker compose pull && docker compose up -d` |
| Выход из сети | `… node exit --node-data /var/lib/fs-node` (раздел «Выход из сети») |

`cli node stop` останавливает демон, но не контейнер: с
`restart: unless-stopped` Docker запустит его снова. Чтобы узел действительно
встал, останавливайте контейнер: `docker compose stop node`.

Изменения в `environment` и `volumes` применяются только при пересоздании
контейнера: `docker compose up -d` (не `restart`). Данные и ключи лежат в
томе `backpeer-node-data`, поэтому пересоздание их не трогает.

**Пределы и пауза.** `pause` полезен, когда канал нужен для другого:
начатые передачи завершаются, новые не начинаются, узел остаётся на связи.
Пределы задаются в байтах в секунду и общие на все соединения. Постоянные
пределы — в `environment` (`FS_NODE_LIMITS_*`), временные — командой
`limits`; после перезапуска возвращаются постоянные.

## Диск и данные

В томе `backpeer-node-data` лежат ключи узла, сертификат, журналы, индекс
фрагментов и сами фрагменты. Пересоздание контейнера и обновление образа
том не трогают; удаление тома (`docker compose down -v` или
`docker volume rm`) уничтожает узел безвозвратно — для координатора это
потеря узла, а его фрагменты восстановятся на других узлах ремонтом.

**Резервная копия.** Ключи узла лежат в томе без пароля (демон работает без
человека), поэтому копия тома — это и есть узел: храните её как секрет. Без
крайней необходимости копию не восстанавливайте на другую машину
одновременно с работающим узлом — получится два узла с одним ключом.

```sh
docker compose stop node
docker run --rm -v backpeer-node-data:/data -v "$PWD":/backup alpine \
  tar czf "/backup/backpeer-node-$(date +%F).tar.gz" -C /data .
docker compose start node
```

Восстановление — на остановленном узле:

```sh
docker compose stop node
docker run --rm -v backpeer-node-data:/data -v "$PWD":/backup alpine \
  sh -c 'rm -rf /data/* && tar xzf /backup/backpeer-node-2026-11-07.tar.gz -C /data'
docker compose start node
```

**Фрагменты на другом диске.** Том с ключами можно оставить на системном
диске, а фрагменты положить на большой. Смонтируйте каталог хоста и укажите
его в `FS_NODE_STORAGE_DIR`:

```sh
sudo mkdir -p /srv/backpeer/fragments
sudo chown 10003:10003 /srv/backpeer/fragments
sudo chmod 700 /srv/backpeer/fragments
```

```yaml
    environment:
      FS_NODE_STORAGE_DIR: /srv/backpeer/fragments
    volumes:
      - node-data:/var/lib/fs-node
      - /srv/backpeer/fragments:/srv/backpeer/fragments
```

Каталог должен принадлежать uid 10003: другой владелец — узел не запустится
или не сможет писать. Переносить уже накопленные фрагменты нужно на
остановленном узле: скопируйте `fragments/` и `fragments.db` в новый каталог
с сохранением прав и только потом меняйте настройку. Иначе индекс и файлы
разойдутся, и координатор получит отчёт о повреждённых фрагментах.

**Место кончилось.** Узел не принимает фрагмент, если после него на диске
останется меньше `FS_NODE_STORAGE_FREE_RESERVE_BYTES`. Занятое место видно в
`cli node status`; освободить его можно, уменьшив квоту (лишние фрагменты
координатор перенесёт) или добавив диск.

## Обновление

Образы публикуются на тег версии и `latest`. Для постоянного узла лучше
закрепить версию в `.env` (`BACKPEER_VERSION=v0.0.3`) и обновляться
сознательно:

```sh
docker compose pull
docker compose up -d
```

Обновление пересоздаёт контейнер, данные и ключи остаются в томе. Откат —
вернуть прежний тег в `.env` и снова `docker compose up -d`; ключи и
фрагменты от этого не меняются, совместимость протокола проверяется при
соединении. Перед обновлением полезно сделать резервную копию тома и
посмотреть `docker compose logs` после запуска.

## Выход из сети

Если узел больше не нужен, не удаляйте том сразу: сначала объявите выход.
Координатор перестанет размещать на узле фрагменты и перенесёт уже
хранящиеся на другие узлы.

```sh
docker compose --profile tools run --rm cli \
  node exit --node-data /var/lib/fs-node
docker compose --profile tools run --rm cli \
  node status --node-data /var/lib/fs-node
```

Перенос идёт, пока узел работает; в `cli node status` видно, сколько фрагментов
осталось. Не выключайте узел до конца переноса — выключенный узел через
72 часа считается потерянным, и его фрагменты восстанавливает ремонт. Когда
переносить нечего, демон удаляет фрагменты, останавливается и больше не
запускается с этой папкой данных. После этого уберите контейнер и том:

```sh
docker compose stop node
docker compose down
docker volume rm backpeer-node-data
```

`node exit --cancel` отменяет выход; уже перенесённые фрагменты остаются на
новых узлах. Чтобы снова участвовать, создайте новый том и привяжите новый
узел: `docker compose run --rm node pair` (прежний узел восстановить нельзя).

## Если что-то не так

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| Контейнер перезапускается каждые несколько секунд | Нет `FS_NODE_COORDINATOR_URL`, битые права на томе, занят порт 7340 | `docker compose logs --tail=100 node`; проверьте `.env`, владельца тома (uid 10003) и занятость порта |
| `unhealthy` в `docker compose ps` | Демон не отвечает по локальному API | `docker compose logs`; проверьте, что контейнер не убит по таймауту остановки (`stop_grace_period`) |
| `docker compose pull` отвечает `401` | Образы в GHCR ещё не опубликованы или закрыты | Соберите образ из исходников (`docker build -f packages/node/Dockerfile -t … .`) или используйте реестр своей сборки |
| Привязка не выдаёт код | Координатор недоступен или в нём выключена привязка | Проверьте адрес и `docker compose run --rm node pair`; при необходимости используйте сертификат |
| Код привязки не принимается | Истекли 10 минут | Запустите `pair` заново и введите новый код |
| «Узел привязан», но фрагменты не приходят | Нет доступа извне и не включён relay | Проверьте проброс порта и `FS_NODE_LISTEN_ENDPOINTS`; оставьте `FS_NODE_LISTEN_RELAY=auto` |
| «ёмкость меньше 100000000000» в журнале | `FS_NODE_STORAGE_QUOTA_BYTES` меньше минимума координатора | Увеличьте квоту и место на диске |
| `permission denied` в журнале | Том или каталог фрагментов принадлежит другому пользователю | `sudo chown -R 10003:10003` на каталоге фрагментов, том пересоздавать не нужно |
| `node.lock` и узел не стартует | С тем же томом работает другой контейнер | Остановите лишний контейнер: `docker ps` |
| Талоны отклоняются, «подпись не та» | Часы хоста убежали | Включите NTP и перезапустите узел |

Если ничего не помогает, в журнале есть события с типом ошибки, но без
ключей и содержимого фрагментов. Для разбора пригодятся
`docker compose logs --since 1h node` и машинный вывод
`docker compose --profile tools run --rm cli --json node status
--node-data /var/lib/fs-node`.

## Безопасность

- Контейнер работает не от root (uid 10003), с томом прав 0700.
- Ключи узла хранятся в томе без пароля: по ним нельзя расшифровать данные
  клиентов, но можно выдать себя за узел и вредить хранению. Защищайте том,
  резервные копии и доступ к Docker на хосте.
- Наружу нужен только порт 7340; порт координатора и Docker API не
  публикуйте.
- Узел не видит имена и содержимое файлов: шифрование выполняется на
  устройстве клиента.
- Обновляйте образ и хост: узел принимает решения по подписям координатора,
  а не по паролю.
